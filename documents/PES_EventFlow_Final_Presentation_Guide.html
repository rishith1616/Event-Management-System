🛡️ Top Technical Evaluator Questions & Answers

Key architectural questions professors frequently ask, with rock-solid technical answers.

Q1: How do you prevent two students from buying the last remaining ticket at the exact same millisecond?
Answer: "We use MongoDB multi-document ACID transactions with document-level locking (withTransaction). When two concurrent purchase or hold requests hit the server, the query atomically checks { availableTickets: { $gte: quantity } } and decrements the inventory. Only the first transaction acquires the write lock and commits; the second immediately aborts, rolls back, and returns an HTTP 409 Conflict. This is automated and verified in our test suite transaction.test.js."
Q2: What happens if a student starts checkout, holds a seat, and abandons their tab?
Answer: "Every ticket hold has an explicit TTL timestamp (holdExpiresAt = now + 10 minutes). Our server runs an automated background cleanup sweep that finds expired holds, marks them expired, and restores the exact seat quantity back to the event's available pool. Additionally, any attempt to view or book the event triggers an eager lazy sweep."
Q3: How do you satisfy PCI-DSS compliance for card payments?
Answer: "Under PCI-DSS guidelines, web applications should never store raw PANs (card numbers) or CVVs. In PES EventFlow, card credentials are tokenized on the client side into one-way nonces (tok_...). The payload transmitted to our server stores only the token and the masked last 4 digits (**** 1234) for receipt generation. Our automated test pciCompliance.test.js verifies zero 16-digit card numbers exist in MongoDB."
Q4: Why did you choose MERN instead of a relational SQL database for ticketing?
Answer: "PES campus events have polymorphic seating configurations: an Aatmatrisha concert has 3 Opera House levels and VIP pits, while an Aura Hackathon in the MRD Building has lab bench allocations and team squad bundles. MongoDB's document model allows each event to embed rich multi-tier ticket definitions without complex multi-table joins. Crucially, with MongoDB replica set transactions (withTransaction), we maintain strict ACID consistency for inventory and payments while enjoying sub-300ms read performance."
